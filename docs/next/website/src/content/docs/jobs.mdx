---
title: Jobs
description: Run commands on a cron schedule or an interval, with the result recorded and shown inside Flockr.
---

A job is a command that Flockr runs for you on a schedule: sync a tracker every hour, check a build every morning, refresh a cache. The server schedules the job, runs it in the background with a timeout, records the result, and can tell you when it fails. Jobs are global per user, not per workspace.

A job can also publish a [feed](#feeds): a list of items, such as what needs your attention today, that Flockr shows in a sidebar section and in the Feed overlay, with actions you can run on each item.

## Overview

- Each job lives in `~/.config/flockr/jobs/<id>/job.toml`. Debug builds use `flockr-dev` instead of `flockr`.
- `flockr job list` shows every job. `prefix+t` opens the Jobs overlay inside Flockr. `flockr feed list` shows the jobs' feeds, and `prefix+f` opens the Feed overlay.
- A job runs with your login-shell environment by default, so credentials you keep in `~/.zshrc` are available.
- If Flockr was not running when a job was due, the job runs once when the server starts.
- Flockr ships a few jobs of its own, the [system jobs](#system-jobs). They sit in the same list with source `system`.
- A job can [ask you](#handoff-ask-then-start-an-agent) whether to start an agent after a run. Nothing starts until you say so.
- `flockr job new`, `validate` and `run --dry-run` create, check and try a job without a server; see [Authoring jobs](#authoring-jobs). A skill teaches Claude the same workflow: [Authoring with Claude](#authoring-with-claude).

## Define a job

```toml
# ~/.config/flockr/jobs/workbox-sync/job.toml
title = "workbox sync"
command = ["workbox", "sync"]      # argv; use ["sh", "-c", "..."] for a shell command
schedule = "0 10 * * 1-5"          # cron, five fields, local time  (or: every = "1h")
timeout = "10m"
enabled = true
notify = "on_failure"              # never | on_failure | on_change | always
```

| Key | Meaning |
| --- | --- |
| `id` | Optional. When present it must equal the directory name. Letters, digits, `.`, `_` and `-`, up to 120 characters, starting with a letter or digit. |
| `title` | Name shown in lists and toasts. Defaults to the id. |
| `command` | Required argv array. The first element is the program. Flockr does not run a shell unless you do. |
| `schedule` or `every` | Required: exactly one of them. See [Schedules](#schedules). |
| `timeout` | Default `10m`, minimum `1s`, maximum `24h`. When it expires Flockr stops the command and everything it started. |
| `enabled` | Default `true`. |
| `env`, `env_file`, `[env]` | See [Environment](#environment). |
| `cwd` | Working directory. Defaults to the job directory. `~` and relative paths (relative to the job directory) work. |
| `notify` | See [Notifications](#notifications). Default `on_failure`. |
| `feed` | Optional table that gives the job a [feed](#feeds): `command` (required argv), `title`, and an optional `[feed.work]` table for [working on selected items](#work-on-items-feedwork). |
| `handoff` | Optional table: after a run, ask whether to start an agent tab. See [Handoff](#handoff-ask-then-start-an-agent). |

Unknown keys are errors, so a typo such as `evry` is reported instead of ignored. Problems are listed together, with the file and the key, in `flockr job list` and in the Jobs overlay:

```text
broken   invalid   -   -   schedule: invalid cron "0 10 * *": expected 5 fields (minute hour day-of-month month day-of-week), found 4
```

Edits are picked up within about 30 seconds, or at once by `flockr server reload-config`.

## Authoring jobs

Three commands take a job from nothing to enabled. They read and write job files directly and work without a running server.

```sh
flockr job new nightly --template shell --every 1h --feed --handoff
flockr job validate nightly --run-feed
flockr job run nightly --dry-run
flockr job enable nightly
```

### Create: `flockr job new`

`flockr job new <id> [--template shell|python|rust|workbox] [--every 1h | --schedule "CRON"] [--feed] [--handoff]` writes `~/.config/flockr/jobs/<id>/` (the `flockr-dev` directory in debug builds). It refuses to touch an id that already exists, and the job is always written with `enabled = false`.

| Template | Files | Command |
| --- | --- | --- |
| `shell` (default) | `job.toml`, `run.sh` | `["sh", "run.sh"]` |
| `python` | `job.toml`, `run.py` | `["python3", "run.py"]` |
| `rust` | `job.toml`, `job.rs` | `["rust-script", "job.rs"]` |
| `workbox` | `job.toml`, `prompt.md`: the [workbox-sync example](https://github.com/Rambarani/flockr/tree/master/examples/jobs/workbox-sync), with a feed and a handoff | `["workbox", "sync"]` |

- `--every` takes an interval and `--schedule` a five-field cron expression (one of them, default `every = "1h"`).
- `--feed` adds a feed stub that prints a valid [feed](#feed-format-version-1) and a `[feed]` table. `--handoff` adds a `[handoff]` table and a `prompt.md` template. The generated `job.toml` explains every key in comments, and keys you did not use are present as comments.
- The `rust` template is a single file run by [`rust-script`](https://rust-script.org), which compiles it on first use. `job new` tells you how to install it (`cargo install rust-script`) when it is missing. `flockr job build <id>` compiles ahead of time with `rust-script --build-only`, so the first scheduled run is not slow.

### Check: `flockr job validate`

`flockr job validate [<id>|<path>] [--run-feed] [--json]` checks one job, a job directory or `job.toml` by path, or every job when given nothing. It exits non-zero when any job has an error.

- Everything the server's own parser reports (unknown keys, bad schedules, bad `handoff.when`).
- The command resolves on the job's `PATH`, using the job's environment mode: `login-shell` captures your login shell here, the way the server does; if that fails the report says it fell back to the server environment. Scripts such as `run.sh` and the `prompt_file` exist, `cwd` and `env_file` exist, and a cron expression that never fires is an error.
- Handoff templates use only [known variables](#templates) (`{{context.*}}` draws a warning, since it only has a value with a dynamic handoff), `{prompt_file}` has a prompt, and `{{count}}` or `{{feed_json}}` without a `[feed]` draw a warning.
- `[feed.work]` templates use only [its variables](#work-on-items-feedwork) (`{{items}}`, `{{item.field.<label>}}` and the others), the prompt file exists and is not empty, and a `cwd` without placeholders that does not exist draws a warning (work tabs fall back to the job's `cwd` or your home directory).
- The next three run times in local time, and a warning when `timeout` is not shorter than `every`.
- With `--run-feed`, the feed command runs and its output is checked: stdout must be one JSON object, and the parser's diagnostics (cut text, dropped actions, reserved keys) are listed as warnings. Without it the feed command is not executed.

`--json` prints `{"ok": bool, "jobs": [...]}` for tools.

### Try: `flockr job run <id> --dry-run`

A dry run executes the job once in the foreground, with the job's real environment, working directory and `timeout`, and prints what the server would have done with the result. **It runs the real command**, so a job that changes data changes it. Use `--no-exec` for a run that executes nothing.

- The exit code, duration, stdout and stderr, and the feed command's parsed summary (items, unread count, diagnostics), when the job succeeded.
- The evaluated [handoff](#handoff-ask-then-start-an-agent): the question, tab title, directory, the agent command that would be typed, and the rendered prompt, with warnings for variables that had no value. A first run counts as a change for `when = "on_change"`.
- For a job with a `[feed]`, the `w` preview: the tab title, directory, agent command and prompt that [working on items](#work-on-items-feedwork) would start for the first two feed items (the built-in defaults when there is no `[feed.work]`).
- Nothing is recorded: no run in the history, no feed stored, no toast, no decision. `FLOCKR_JOB_STATE_DIR` points at a scratch directory that is deleted afterwards.
- `--no-exec` skips the command and the feed and renders the handoff for a successful run with empty stdout.
- The exit code is non-zero when the command fails, the feed is unusable or the handoff cannot be built.

### Schemas

`flockr job schema` prints a JSON Schema for `job.toml` (including `[handoff]`, `[env]`, the feed table and, under `$defs.jobsConfig`, the `[jobs.system.*]` section of `config.toml`); `flockr job schema --feed` prints the one for feed output. Both are generated from the constants the parsers use and checked by tests, and committed as [`docs/next/api/flockr-job.schema.json`](https://github.com/Rambarani/flockr/blob/master/docs/next/api/flockr-job.schema.json) and [`flockr-feed.schema.json`](https://github.com/Rambarani/flockr/blob/master/docs/next/api/flockr-feed.schema.json). Editors that understand JSON Schema for TOML can use them for completion.

## Authoring with Claude

Flockr ships a skill, `flockr-jobs`, that teaches Claude (or another coding agent) this workflow: the concepts, the `job new`, `validate`, `run --dry-run` and `enable` loop, the `job.toml` reference, the feed contract (stdout must be only the JSON object, single-character action keys, reserved keys, caps), handoff templates, environment rules, debugging with `flockr job logs` and `flockr decision list`, and two worked examples. Once it is installed, ask for what you want in plain words ("check my open PR count every 30 minutes and tell me when it changes") and the agent writes, validates and dry-runs the job for you. It does not enable a job without asking.

The skill is separate from the [`flockr` skill](/docs/agent-skill/) that controls panes. Install it with `npx skills`, as for that one:

```sh
npx skills add Rambarani/flockr --skill flockr-jobs -g
```

Or copy the copy that is bundled with your binary into a Claude Code skills directory:

```sh
mkdir -p ~/.claude/skills/flockr-jobs
flockr job skill > ~/.claude/skills/flockr-jobs/SKILL.md
```

`flockr job skill` prints the file that matches your installed Flockr. For agents without a skill system, paste its output into the project or user instructions. Flockr does not install the skill for you.

## Schedules

`every` takes `30s`-style durations such as `5m`, `1h`, `1h30m` or `1d`. The minimum is `1m`. The next run is one interval after the previous run started.

`schedule` is a five-field cron expression in local time: `minute hour day-of-month month day-of-week`.

- Each field accepts `*`, a value, a range `a-b`, a list `a,b`, and steps `*/n` or `a-b/n`.
- Month and weekday names work (`jan`, `mon-fri`). Weekday `7` is Sunday.
- When both day fields are restricted, a day matches if either does (`0 0 1 * mon` is the 1st and every Monday).
- `@daily`-style macros are not supported.

Daylight saving time: a time that does not exist (spring forward) runs at the instant the clock jumps, and a time that happens twice (fall back) runs once, on its first pass. The schedule follows the wall clock forward, so the repeated hour is not scheduled again.

Missed runs: when the server starts, a job whose last scheduled time passed since its last run starts once, however many times it was missed. A job that has never run counts from when its `job.toml` was written.

A job never overlaps itself. If a run is still going when the next one is due, the new run is skipped and recorded as `skipped: still running`.

## Environment

`env = "login-shell"` is the default. Flockr runs `$SHELL -l -i -c` once, with a marker around `env -0`, and gives jobs the resulting variables. The shell is interactive (`-i`) because zsh reads `~/.zshrc` only for interactive shells. Only the text between the markers is used, so banners and prompt frameworks cannot corrupt it.

- The capture has a 5 second timeout and is cached for 10 minutes. `flockr job env refresh` captures again at once.
- If the capture fails or times out, jobs use the server environment and the run record says why.
- Values are kept in memory only. They are never written to disk, to logs, or to API responses. Run records store a count such as `login-shell (214 variables)`.
- Job output is stored, though. Do not print secrets from a job.

`env = "server"` uses the environment of the Flockr server process. A job file cannot hold both `env = "..."` and an `[env]` table, so with a table put the mode inside it:

```toml
env_file = "secrets.env"          # KEY=VALUE lines; relative to the job directory

[env]
mode = "server"                   # optional; default login-shell
LOG_LEVEL = "debug"               # non-secret overrides
```

Order of precedence, last wins: the base environment, `env_file`, the `[env]` table, then the variables Flockr always sets: `FLOCKR_ENV`, `FLOCKR_SOCKET_PATH`, `FLOCKR_BIN_PATH`, `FLOCKR_JOB_ID`, `FLOCKR_JOB_DIR` and `FLOCKR_JOB_STATE_DIR`. A variable literally named `mode` cannot be set in the `[env]` table.

## Notifications

`notify` decides when a finished run shows a toast, through the same path as other Flockr toasts and `[ui.toast] delivery`:

| Value | Toast when |
| --- | --- |
| `never` | Never. |
| `on_failure` | The run failed, timed out or could not start. This is the default. |
| `on_change` | The status or the stdout text differs from the previous run. The first run only when it failed. |
| `always` | Every run. |

The toast shows the job title and a short result such as `ok in 1.2s · 3 items` or `failed (exit 3) in 4.1s · connection refused`.

## Runs and state

State lives in `<state dir>/jobs/<id>/state.json`, written atomically. It holds the last 20 runs with start, duration, exit code, and the last 16 KiB of stdout and stderr of each, plus any `flockr job enable/disable` override. Output beyond the cap keeps the end.

`flockr job enable` and `disable` override `enabled` in the file until you set the file's value again. Enabling restarts the schedule from now, so a job that was off for a week does not run at once. `flockr job run` works for disabled jobs too.

A stdout line that starts with `{"flockr_handoff":` is a [dynamic handoff](#dynamic-handoff). It is kept verbatim in the run record, and the handoff reads it after the run.

Feed output does not appear in the run record: a feed refresh is not a run and does not count in the history.

## System jobs

System jobs are jobs built into Flockr. Their ids start with `system.`, they run through the same scheduler and runner as your jobs, and they show in `flockr job list`, `flockr job status` and the Jobs overlay with source `system`. They have no `job.toml`; their timing comes from config.

| Job | What it does |
| --- | --- |
| `system.upstream-herdr` | Checks the upstream herdr releases (once a day by default) and asks whether to copy the updates. It replaces the fixed upstream timer; see [Upstream herdr watcher](/docs/configuration/#upstream-herdr-watcher). |

```toml
# config.toml
[jobs.system.upstream-herdr]
every = "24h"          # or schedule = "0 9 * * *"; exactly one of them
enabled = true
notify = "never"       # never | on_failure | on_change | always
```

- **Timing and switches.** `every` and `schedule` take the same values as in a job file; `enabled` and `notify` work as there. A bad value is reported as a config diagnostic and the default stays. A table that names no system job is reported too.
- **The old keys keep working.** `[upstream] enabled` switches the upstream job and `[upstream] check_interval_hours` is its default interval. The interval key is deprecated and draws a diagnostic. `[jobs.system.upstream-herdr]` wins over both.
- **First run.** A system job that has never run is due at once when the server starts, then follows its schedule.
- **Run by hand.** `flockr job run system.upstream-herdr --wait`, `flockr job logs system.upstream-herdr`, `flockr job disable system.upstream-herdr` work like for any job.

## Change when a job runs

You can change a job's timing at any time, in the job file or without opening it:

- **Jobs overlay.** Select the job, press `t`, type a schedule and press `enter`. The prompt starts with the current schedule and checks what you type as you type: `every 2h` (or just `2h`) is an interval of at least a minute, anything else must be a five-field cron expression such as `0 9 * * 1-5`. Nothing is sent until it is valid.
- **Command line.** `flockr job schedule <id> every 2h` or `flockr job schedule <id> "0 9 * * 1-5"`.

Where the new schedule is written:

| Job | Written to |
| --- | --- |
| System job | `[jobs.system.<name>]` in `config.toml`: `every = "2h"` or `schedule = "..."`, and the other key is removed. The rest of the file stays as it was. |
| Job with a `job.toml` | The existing `schedule` or `every` line of that file, changed in place, keeping its indentation and trailing comment. Nothing else in the file is touched. Flockr re-reads the edited text and refuses to write it unless it is the original document with only that key changed. |
| Anything else | An override stored in the job's state (`state.json`), and Flockr says so. That is where plugin jobs go, and any `job.toml` whose schedule is written in a form the line editor does not understand (a multi-line string, both keys set, or no key at all). `flockr job status` marks the override. Editing the file and running `flockr job schedule` again moves it back into the file. |

The change applies at once, without a restart, and the schedule starts again from now: a job moved to `every 5m` runs in five minutes, not immediately for the time the old interval had already waited.

## Handoff: ask, then start an agent

A job can end with a question for you. After a run, Flockr decides whether the job has something worth your attention. If it does, it records a **decision**, shows a toast with the question, and waits. It never starts an agent on its own: you answer **Start**, **Snooze 1h** or **Dismiss**, and **Start** opens a tab in the directory you chose and runs your agent with a prompt built from the job's output.

```toml
# ~/.config/flockr/jobs/workbox-sync/job.toml
[handoff]
when = "on_change"                 # on_success | on_change | on_failure | always | "exit:<code>"
ask = "{{count}} items need you. Start Claude?"
agent_command = "claude"           # default; any command, see below
cwd = "~/Desktop/poc/workbox"      # the tab's working directory; default: the job's cwd
tab_title = "workbox · {{date}}"   # default: "{{job.title}} · {{date}}"
prompt_file = "prompt.md"          # a template in the job directory ...
# prompt = "Triage {{count}} items:\n{{feed_json}}"   # ... or an inline template (not both)
# submit = true                    # default; false leaves the prompt as an unsent draft
# prefill = "paste"                # with submit = false: "paste" (default) or "mention"
```

| Key | Meaning |
| --- | --- |
| `when` | Which runs ask. `on_success`: the run succeeded. `on_failure`: it failed, timed out or could not start. `always`: every run. `exit:<code>`: it exited with that code. `on_change`: the run's stdout or the job's feed differs from the previous run's (the first run counts as a change). Default `on_change`. |
| `ask` | The question, a template. Default `<job title> has something for you. Start an agent?` |
| `agent_command` | What the tab runs. Default `claude`. A template; values filled into it are shell-quoted. |
| `submit` | Default `true`: the prompt is passed to the agent, which runs it at once, as a handoff always did (an upstream sync must run). `false`: the agent starts alone and the prompt is typed into its input box as a draft, without Enter, so you can add to it. Has no effect when `agent_command` contains `{prompt_file}`. |
| `prefill` | With `submit = false`: `"paste"` (default) types the whole prompt as a bracketed paste, `"mention"` types one line, `@<prompt file>`. Not allowed with `submit = true`. |
| `cwd` | The tab's working directory, a template. `~` and paths relative to the job directory work. It must exist when you press Start. |
| `tab_title` | The tab's name, a template, cut to 60 characters. |
| `prompt_file` or `prompt` | The prompt template: a file in the job directory, or inline text. At most one. Without either the agent starts with no prompt. |

### The prompt reaches the agent as a file

The rendered prompt is written to `<state dir>/jobs/<id>/handoffs/<run>.md` (the newest 50 per job are kept), and the agent gets the file, never a huge argument. Flockr starts the agent like `flockr upstream sync` always did:

- If `agent_command` contains `{prompt_file}`, it is replaced by the quoted path of the file: `agent_command = "claude --append-system-prompt-file {prompt_file}"`.
- Otherwise the prompt text is passed as the first argument: `claude "$(cat '<file>')"`.
- With no prompt at all the command runs exactly as written. (The upstream decision works this way: its command is `flockr upstream sync <tag>`, which builds its own prompt.)
- With `submit = false` and no `{prompt_file}` in the command, the agent starts alone and the prompt is typed afterwards as a draft; see [Leave the prompt as a draft](#leave-the-prompt-as-a-draft).

The command is typed into the new tab's shell, so the agent owns a real terminal and you can watch and steer it.

### Leave the prompt as a draft

Passing the prompt as an argument makes agents such as Claude Code submit it at once. With `submit = false` (the default for [`[feed.work]`](#work-on-items-feedwork), opt-in for a handoff) Flockr starts the agent with no prompt and puts the prompt in its input box without pressing Enter, so you add your own instructions and press Enter yourself.

- **Readiness.** Flockr does not sleep on its server thread. It queues the prompt and checks the new pane on the server's timer every 100 ms. For an agent Flockr detects (the program name matches a known agent such as `claude`), it waits until the pane is an agent terminal with status idle or done on two checks in a row, the same status `flockr agent wait` uses, and until the terminal has turned bracketed paste on. After 20 seconds it types anyway and logs a warning. For an agent Flockr cannot detect there is nothing to wait for, so it waits a fixed 1.5 seconds.
- **Typing.** The text goes in as a bracketed paste (`ESC[200~ … ESC[201~`) with no Enter after it. With `prefill = "paste"` (default) that is the whole prompt; Claude Code shows a long paste as `[Pasted text #1 +N lines]`, which is fine. With `prefill = "mention"` it is one line, `@<absolute prompt file path> `, followed by a space, so the draft stays compact. A path with whitespace is quoted, `@"<path>" `. If the terminal never turned bracketed paste on, a multi-line prompt would submit at its first newline, so Flockr types the one-line mention instead.
- **`{prompt_file}` wins.** If `agent_command` contains `{prompt_file}`, you chose how the agent receives the file, Flockr cannot know whether that command submits, and `submit` and `prefill` have no effect. `flockr job validate` says so.
- **The mention file.** The prompt file is under the job's state directory, outside your project. Claude Code reads `@` mentions of absolute paths, but it may ask for permission to read a file outside the working directory. If that is a nuisance, use `prefill = "paste"`.

### Templates

`ask`, `agent_command`, `cwd`, `tab_title`, `prompt` and the prompt file use `{{name}}` placeholders:

| Name | Value |
| --- | --- |
| `{{stdout}}` | The run's stdout, without the handoff line, cut to 12,000 characters. |
| `{{stderr_tail}}` | The end of stderr, at most 4,000 characters. |
| `{{exit_code}}` | The exit code, empty when the run had none (timeout, signal, not started). |
| `{{feed_json}}` | The job's feed after this run's refresh as `{"title", "total", "items": [...]}` without action commands, cut to 48,000 characters by dropping items from the end (then `"truncated": true`). `{"items":[]}` when the job has no feed. |
| `{{count}}` | `context.count` of a dynamic handoff if it has one, otherwise the feed's unread count, otherwise 0. |
| `{{date}}` | Today's local date, `YYYY-MM-DD`. |
| `{{job.id}}`, `{{job.title}}`, `{{run.id}}` | The job and the run. |
| `{{context.<path>}}` | A value from the dynamic handoff's `context` object, `{{context.tag}}` or `{{context.release.name}}`. Strings as they are, other values as JSON, each cut to 8,000 characters. |

A name with no value renders as empty text and is logged. Substitution is a single pass: a value is never searched for placeholders again, so job output cannot inject more. The prompt is cut at 200,000 characters. The `ask` and the tab title are flattened to one line.

### Dynamic handoff

A job can decide by itself. If its stdout has a line that starts with `{"flockr_handoff":`, the last one is the handoff: it asks regardless of `when`, even without a `[handoff]` table.

```json
{"flockr_handoff": {"ask": "herdr {{context.tag}} is out. Copy updates?",
  "agent_command": "flockr upstream sync {{context.tag}}",
  "cwd": "~/src/flockr", "tab_title": "upstream-sync {{context.tag}}",
  "context": {"tag": "v0.9.7", "count": 3, "notes": "..."}}}
```

Its fields (`ask`, `agent_command`, `cwd`, `tab_title`, `prompt`, `prompt_file`) override the table's and may use the same templates, and `context` is any JSON object for `{{context.*}}`. A field of the wrong type is ignored with a log entry. The upstream watcher is the first user.

### When Flockr asks

After a run, once its feed refresh (if the job has one) is done, so `{{feed_json}}` and `on_change` see the new items. A decision is dropped when the same job already has one with the same content (same question, command, directory, title and prompt), whether pending or answered, so a job that keeps printing the same thing asks once. If the handoff cannot be built (an unreadable prompt file, `{prompt_file}` without a prompt) you get a toast saying so and no decision.

## Decisions

A decision is a question a job asked. It stays until you answer, because you may be away: the list is kept in `<state dir>/decisions.json` and survives restarts. At most 50 are kept; when the list is full the oldest answered one goes first, then the oldest unanswered one.

You are told by:

- a toast with the question, in the attention style, delivered like other toasts (`[ui.toast] delivery`: in Flockr, through the terminal, or the OS). With `off` there is no popup, so rely on the badge and the list below.
- the badge on the Jobs overlay's title (`jobs  [decisions (2)]`) and a `●1` on the job's row.
- **decisions (N)** in the command palette.
- `flockr decision list`.

Open the **Decisions** tab with `prefix+t`, then `tab`:

| Key | Action |
| --- | --- |
| `enter` or `s` | **Start**: open the tab and run the agent. |
| `z` | **Snooze** for an hour. The decision hides, then comes back as pending with a new toast. |
| `x` | **Dismiss**. |
| `p` | Preview the agent command, directory, tab title and rendered prompt. |

**Start** opens a tab in the decision's directory (`~` expanded), titled `tab_title`, and types the agent command into it. The tab runs in the active workspace and takes focus. The command gets the job's environment rules: the cached login-shell variables (when already captured), `env_file`, the `[env]` table and the `FLOCKR_*` job variables. If the directory does not exist, the prompt file is gone, or there is no workspace, nothing opens: the reason is recorded on the decision, shown in the overlay and by `flockr decision list`, and the decision stays pending, so you can fix the cause and press Start again. A started decision records `started in tab <id>` and leaves the list; `flockr decision list --all` still shows it.

```sh
flockr decision list [--all] [--json]
flockr decision start d3
flockr decision snooze d3 --for 2h
flockr decision dismiss d3
```

The upstream watcher's **Copy updates** is a decision of `system.upstream-herdr` whose command is `flockr upstream sync <tag>`; `flockr upstream copy` and the review popup start it, and Skip dismisses it.

## Feeds

A feed is a list of items a job prints, for example the unread items of a tracker. Flockr stores the latest list, shows it, and keeps it up to date.

```toml
# ~/.config/flockr/jobs/workbox-sync/job.toml
title = "workbox sync"
command = ["workbox", "sync"]
every = "1h"

[feed]
command = ["sh", "-c", "workbox list --json --include-done | flockr feed adapt workbox --title 'Today (workbox)'"]
title = "Today (workbox)"          # optional; wins over the title the command prints
```

A complete example, with a stub to try it without the real tool, is in `examples/jobs/workbox-sync/` in the Flockr repository; `flockr job new workbox-sync --template workbox` writes it for you.

### When the feed refreshes

- After every **successful** run of the job (a failed run keeps the feed it had).
- On demand: `flockr feed refresh <job>`, `R` in the Feed overlay, or **refresh feed** in the command palette.
- After an item action, see [Actions](#actions).
- Once when the server starts, for an enabled job whose feed has never been read.

The feed command runs exactly like the job: same environment rules (`env`, `env_file`, `[env]`, the `FLOCKR_*` variables), same working directory, and the job's `timeout`, after which the command and everything it started are stopped. At most one feed task runs per job at a time; a second request is refused with the reason. Asking for a refresh while the job itself is running is refused too, because the feed refreshes when the run finishes.

The latest feed is stored in `<state dir>/jobs/<id>/feed.json`, written atomically, and survives restarts. When a refresh fails (exit code, timeout, output that is not a valid feed), Flockr **keeps the last good items and marks the feed stale**: the sidebar header shows `!`, the overlay shows `stale:` with the reason, and `flockr feed list` says `stale, last good 5m ago`. The next good refresh clears it.

### Feed format, version 1

The command prints one JSON object on stdout (at most 4 MiB):

```json
{"version": 1, "title": "Today (workbox)",
 "groups": [{"id": "mentions", "title": "JIRA Mentions"}],
 "items": [
  {"id": "jira:NH-1412", "title": "Fix login redirect", "group": "mentions",
   "subtitle": "jira · mention", "state": "unread", "badge": "NH-1412",
   "url": "https://example.atlassian.net/browse/NH-1412",
   "updated_at": "2026-10-18T08:30:00Z",
   "body": "Can you look at the redirect?\nIt blocks the release.",
   "fields": [{"label": "Source", "value": "jira"}, {"label": "Status", "value": "In Progress"}],
   "actions": [
     {"key": "d", "title": "done", "command": ["workbox", "mark", "jira:NH-1412", "done"]}
   ]}
]}
```

| Field | Meaning |
| --- | --- |
| `version` | `1`. A missing version is read as 1 with a note; any other number is an error. |
| `title` | The feed's name. The job's `feed.title` wins, then this, then the job title. |
| `groups` | Optional list of up to 16 categories, in tab order: `{"id", "title", "short_title"}` (`id` up to 40 characters and unique, `title` up to 60 and defaulting to the id, `short_title` up to 20, used where space is tight). See [Groups](#groups-category-tabs). |
| `items[].id` | Required, unique within the feed. Duplicates keep the first. |
| `items[].group` | Optional id of one of the feed's `groups` (up to 40 characters). Missing or undeclared ids go to an implicit `other` group. Ignored in a feed without `groups`. |
| `items[].also_groups` | Optional list of up to 4 more group ids the item also belongs to, so it shows under those category tabs as well as under its `group`. See [Groups](#groups-category-tabs). |
| `items[].title` | Shown in rows. Defaults to the id. |
| `items[].subtitle`, `badge` | Secondary text, and a short label such as a ticket key. |
| `items[].state` | `unread`, `read` (default), `done`, `warn` or `error`. It sets the dot and the unread count. An unknown state becomes `read`. |
| `items[].url` | An `http://` or `https://` link. Other schemes are ignored. |
| `items[].updated_at` | RFC 3339 time, shown as an age in the overlay. |
| `items[].body` | Optional plain text for the detail pane. Line breaks are kept; it is cut at 8 KiB. |
| `items[].fields` | Optional list of up to 12 `{"label", "value"}` pairs, shown as a table in the detail pane (labels up to 40 characters, values up to 500). An entry without both is dropped with a note. |
| `items[].actions` | Up to 8 actions, see [Actions](#actions). |

Unknown fields are ignored, so newer producers keep working. Limits: 500 items (the rest are dropped), 200 characters for `id` and `title`, 300 for `subtitle`, 40 for `badge`, 2048 for `url`. Control characters are removed and line breaks become spaces (except in `body`). `body`, `fields`, `groups` and `group` were added after the first release of version 1: they are optional, a feed without them stays valid, and an older Flockr ignores them. A bad item (no `id`) or a bad action is dropped with a note instead of failing the feed; the notes show in `flockr feed show` and in the `diagnostics` of the API.

### Actions

An action is `{"key", "title", "command"}` with an optional `"confirm"`: a single visible character that triggers it in the overlay, a label, an argv array, and, for an action that is hard to undo, a question to ask first.

- `key` cannot be `Enter`, `esc`, the arrow keys, `tab`, `space` or any other named key, nor one of `j`, `k`, `q`, `g`, `G`, `R`, `S`, `/`, `x`, `X`, `w` and `W`, which the overlay uses (`x`, `X`, `w` and `W` select items and start work on them; a feed that used one of them for an action loses that action, with a note, and the rest of the item stays). In a feed that declares `groups`, `[`, `]` and the digits `0` to `9` are reserved too (they switch category); a feed without groups can still use them. Keys must be unique within an item. An invalid action is dropped with a note.
- `confirm` is a question of up to 120 characters, for example `"Delete NH-1412 from workbox?"`. When it is set, the Feed overlay and the sidebar right-click menu show it with `y` (or Enter) to run the action and `n` (or Esc) to cancel; nothing runs before the answer. It is a prompt in the client only: `flockr feed action` and the API methods run the action without asking. A feed without `confirm` behaves as before, and an older Flockr ignores the field.
- Running an action starts its command with the job's environment, plus `FLOCKR_FEED_ITEM_ID` and `FLOCKR_FEED_ACTION_KEY`. It gets at most 60 seconds (or the job's timeout when that is shorter). Then the feed command runs again, so the list shows the result. The refresh also runs when the action fails.
- Commands stay on the server: clients send only the job, the item id and the key, and the server looks the command up in the stored feed. A feed that changed since the client looked answers `feed_item_not_found` instead of running something else.
- The outcome (`ok`, or why it failed) is recorded as `last_action` and shown in the overlay's status line, or as a notice when you started the action from the sidebar.

### Adapters

`flockr feed adapt workbox` reads the JSON array printed by `workbox list --json` or `workbox status --json` on stdin and prints a feed:

```sh
workbox list --json | flockr feed adapt workbox --title "Today (workbox)"
workbox list --json --include-done | flockr feed adapt workbox     # plus a Done tab (last 7 days)
workbox list --tab today --json | flockr feed adapt workbox     # only the today tab
```

Each workbox item is also put in a category, from its `source` and `reason` (the same facts workbox's own `classify` uses), and the feed declares these groups in this order:

| Group (id) | Tab title | Items |
| --- | --- | --- |
| `today` | Today | Every item on workbox's today list (`today: true`, the `t` action), listed through `also_groups`: it is also in its own category below. Always declared, first; the Feed overlay shows it even when empty, the sidebar hides empty groups. |
| `new-house-prs` | New House PR Requests (`New House PRs`) | GitHub `review_requested` and `mention`: someone wants you on a PR. |
| `ticket-mentions` | JIRA Mentions | Jira `mention` (and `commented`). |
| `jira-assigned` | New Tickets Assigned (`New Tickets`) | Jira `assigned`. |
| `old-house-prs` | Old House PR Requests (`Old House PRs`) | Bitbucket `review_requested`. |
| `my-prs` | My PRs (activity) (`My PRs`) | `authored`, `changes_requested`, `commented` and `approved` on GitHub and Bitbucket: what others did on your own PRs. |
| `other` (implicit) | Other | Everything else, for example a `status_changed` or `updated` item. Declared, before Done, only when an item needs it. |
| `done` | Done | Items workbox reports as `done: true`, which `workbox list --json --include-done` adds (items marked done in the last 7 days; `--done-days N` changes that). Always declared, last. A done item is only here: not in its category (so category counts exclude it) and not in Today. Its state is `done`, its actions are `u` undo done (`workbox mark <id> undone`) and `D` delete, and its detail has a `Done at` field. |

Workbox puts GitHub `changes_requested`, `commented` and `approved` on its New House tab next to the review requests. They come from its scan of your own open PRs, so the adapter keeps them in their own tab instead of mixing them in with the requests. Jira has no `status_changed` item in workbox, so none is mapped.

Each workbox item becomes a feed item: `id` is the workbox item id, `badge` its key, `state` is `unread` or `read` (`done` for a done item), `url` and `updated_at` pass through, and `subtitle` is `<source> · <reason>` followed by ` · <where>` when there is one (underscores in the reason become spaces). The detail pane gets `fields` for Source, Reason, Where, Status, From (workbox's actor), Key, Snoozed until and Today (yes or no), leaving out the ones the item does not have, and the snippet as `body`; `updated_at` is shown by the pane itself in local time. The actions are `d` done (`workbox mark <id> done`), `s` seen (`workbox mark <id> seen`) and `t` today, which becomes `untoday` for items already on the today list, and `D` delete (`workbox mark <id> delete`, which hides the item permanently; it carries a `confirm` question, so the overlay and the menu ask `y/n` first). `--title` sets the title (default `workbox`) and `--bin` the program the actions run (default `workbox`, resolved on the job's `PATH`). Items without an id are skipped with a warning on stderr; input that is not an array is an error and exits non-zero, so the feed is marked stale instead of emptied.

### Groups (category tabs)

A feed can sort its items into categories. Declare them in `groups` (their order is the tab order) and point each item at one with `group`:

```json
{"version": 1, "groups": [
   {"id": "reviews", "title": "Review Requests", "short_title": "Reviews"},
   {"id": "mentions", "title": "Mentions"}],
 "items": [
   {"id": "a", "title": "Fix login", "group": "reviews"},
   {"id": "b", "title": "Reply Dana", "group": "mentions"},
   {"id": "c", "title": "No group"}]}
```

- Items with no `group`, or one that is not declared (that also draws a note), are collected in an implicit group with the id `other` and the title `Other`, shown after the declared ones and only when it has items. Declare a group with the id `other` to choose its title and place.
- `also_groups` puts an item in more than one group: up to 4 more declared ids besides its `group`. The item shows under each of those tabs; each group's count and unread count include it, the sidebar group rows too, and All counts it once. An id that is not declared, a repeat, or the item's own `group` is ignored (unknown ids with a note); a feed without `groups` ignores the field. The workbox adapter uses it for the Today tab. The API adds the optional `also_groups` to the items of `feed.get`; older servers and clients leave it out, so an older client shows the item only under its `group`.
- Caps: 16 declared groups (the rest are dropped with a note), 40 characters for an id, 60 for a title, 20 for a `short_title`. A bad entry (not an object, no id, a repeated id) is dropped with a note. A feed without `groups` is one flat list, exactly as before.
- The API adds optional fields: `feed.list` and `feed.get` carry `groups` (`id`, `title`, `short_title`, `count`, `unread`) in each feed summary, and each item from `feed.get` carries its `group`. Request shapes are unchanged, and an older server or client simply leaves the fields out.

The Feed overlay shows a [category tab bar](#feed-overlay) and the sidebar shows one row per group.

### Sidebar section

Below the agent list, each feed gets a collapsible section, once the feed has been read:

```text
────────────────────────
 ▾ Today (workbox) 3
  ● NH-1412 Fix login redirect
  ● NH-1388 Review upload retry
  ○ NH-1301 Reply to Dana
   +4 more
```

- The header shows the feed title and its unread count (a dimmed total in parentheses when nothing is unread). `!` marks a stale feed, `…` a refresh in progress.
- Rows show a state dot, the badge and the title. **Click a row** to open its link; an item without a link opens its action menu. **Right-click a row** for **Open link**, one entry per action, **Refresh feed**, **Sync now (run job)**, **Open feed** and **Collapse**; the header's menu has the same last four.
- **Click the header** to collapse or expand the section. The choice is remembered with the other sidebar state (key `feed:<job id>`).
- **Click `+N more`** to open the Feed overlay on that feed.
- A feed with [groups](#groups-category-tabs) shows one compact row per non-empty group instead of item rows: `New House PRs 9 ●3` (the group's short title, its total and its unread count). **Click a group row** to open the Feed overlay on that category. Right-click gives the feed's menu. The section does not fetch the feed's items for the sidebar.
- The section takes rows from the bottom of the sidebar's lower half and never squeezes the agent list below its minimum height: on a short terminal it shrinks to headers, or disappears. The agent list keeps its position, clicks and keys either way.
- The client asks the server for changes every 5 seconds, with the revision it already holds, and only while the expanded sidebar is on screen. A collapsed sidebar, a narrow mobile layout and `enabled = false` cost nothing.

```toml
[ui.sidebar.feeds]
enabled = true                     # default; false hides every feed section
show = "all"                       # default; or ["workbox-sync"] to pick feeds by job id
max_rows = 8                       # item rows per feed before "+N more" (1 to 50)
```

The section is client presentation only: it draws data the server already stores, and a server without feed support simply shows nothing.

### Feed overlay

`prefix+f` (`keys.feed`) or **feed** in the command palette opens a master-detail view. With several feeds, a row of tabs at the top lets you pick one. **feed: &lt;title&gt;** in the palette opens a specific feed.

The list is on the left (state dot, badge, title, age) and the detail pane on the right follows the selection, whether you move with the keys, the wheel or a click. The pane shows the title, the badge and state, the subtitle, the updated time in local time with its age, the link, the item's `fields` as a table and its `body`, and the item's action keys on its last row. The panel needs 100 columns to go side by side; narrower panels stack the pane under the list, and a very short panel shows the list alone until you zoom the pane with `space`.

A feed with [groups](#groups-category-tabs) gets a **category tab bar** under the info line: `All 68 · New House PRs 9 ●3 · JIRA Mentions 4 · …` (counts are totals; `●n` is the unread count). When the full labels do not fit, the unread marks go first, then the names are shortened, and then the bar scrolls so the selected tab is always visible (`‹` and `›` mark hidden tabs). The list, the filter and the detail pane all follow the selected tab, and **click a tab** to select it. Each feed remembers its tab for the session and in the client preferences (key `feedgroup:<job id>:<group id>`); a tab that no longer exists falls back to All.

| Key | Action |
| --- | --- |
| `↑`/`↓`, `j`/`k`, `g`/`G` | Move |
| `[` / `]` | Previous or next category tab (wraps around All; only in a feed with groups) |
| `0`, `1`-`9` | Select All, or the first nine categories (only in a feed with groups) |
| `tab`, `shift+tab`, `←`/`→` | Switch feed |
| `ctrl+d`, `ctrl+u` | Scroll the detail pane (the wheel over the pane does too) |
| `space` | Zoom the detail pane over the whole body and back (`esc` also leaves the zoom) |
| `enter` | Open the item's link |
| `x` | Select or unselect the current item. Selections survive category tabs and the filter, and the header counts them (`3 selected`). A click on the checkmark column, or a ctrl-click on a row, does the same |
| `X` | Clear the selection |
| `w` | [Work on the selected items](#work-on-items-feedwork) (the current item when none is selected): open a tab and start an agent with the items as the prompt |
| `W` | Work on every item of the list as shown: the selected category tab and the filter, up to 50 items. The footer shows the count: `W work all (12)` |
| `/` | Filter by title, subtitle, badge or id within the selected category (`enter` keeps it, `esc` clears it) |
| item action keys | Run that action on the selected item (the selected item's actions are listed at the bottom of the pane) |
| `R` | Refresh the feed (run the feed command again) |
| `S` | Sync now: run the feed's job, then the feed refreshes when the run succeeds. The header shows `syncing…`, and the status line the result |
| `esc` or `q` | `esc` leaves the zoom, then clears the selection, then clears the filter, then closes. `q` closes |

The overlay polls every 2 seconds while it is open. Clicking a row selects it, and clicking the selected row opens its link.

### Work on items (`[feed.work]`)

Select items with `x` (or ctrl-click), press `w`, and Flockr opens a new tab and starts an agent with those items as its prompt. With nothing selected, `w` uses the current item. `W` starts the agent on every item of the list as shown (the selected category tab, narrowed by the filter), for example the whole Today tab of the workbox feed; more than 50 items are cut to the first 50 and the status line says so. In the sidebar, right-click a category row and choose **Work on all in <tab>** for the same. The overlay closes so the new tab, which is focused, is in view, and a notice says `opened claude with 3 items as a draft — add your note and press Enter` (`started claude with 3 items in tab …` when `submit = true`). The server does the work through the `feed.work` API method, with the same code as a decision's Start: the tab is typed into like any shell, so the agent owns a real terminal, and it starts with the job's environment rules (your login shell's variables by default). Nothing is stored in the feed.

Everything is optional. Without a `[feed.work]` table, `claude` starts in the job's `cwd` when the job file sets one, else your home directory, with the built-in prompt:

```text
Here are 3 items from Today (workbox) I want to work on:

1. NH-1 — Fix login
   Link: https://…
   …

Read each link/ticket, summarize what each needs, and propose a plan. Ask before changing code.
```

(For a single item it reads `Here is 1 item from … I want to work on:` and `Read the link/ticket, summarize what it needs, …`.)

```toml
[feed.work]
agent_command = "claude"                              # default; {prompt_file} puts the prompt file anywhere in the command
cwd = "~/code/{{item.field.repo}}"           # default: the job's cwd, else $HOME
tab_title = "{{job.title}} · {{count}} items"         # default
# prompt = "Review these:\n{{items}}"                 # inline template ...
prompt_file = "work.md"                               # ... or a file next to job.toml (not both)
# submit = false                                      # default: the prompt is a draft you send yourself
# prefill = "paste"                                   # with submit = false: "paste" (default) or "mention"
```

| Key | Meaning |
| --- | --- |
| `agent_command` | The agent CLI. `{prompt_file}` expands to the quoted prompt path (`submit` and `prefill` then have no effect). Without it, `submit = true` passes the prompt as the first argument, as `claude "$(cat <file>)"`; `submit = false` starts the agent alone. Values from templates are shell-quoted. Default `claude`. |
| `submit` | Default `false`: start the agent with no prompt and [type the prompt into its input box as a draft](#leave-the-prompt-as-a-draft), without Enter, so you add your own instructions and press Enter. `true`: the agent runs the prompt at once. |
| `prefill` | With `submit = false`: `"paste"` (default, the whole prompt as a bracketed paste) or `"mention"` (one line, `@<prompt file>`). Not allowed with `submit = true`. |
| `cwd` | Directory of the new tab; `~` and templates work. A directory that does not exist falls back to the default, and the notice says so. |
| `tab_title` | Title of the new tab, one line, at most 60 characters. |
| `prompt`, `prompt_file` | The prompt template, inline or a file relative to the job directory. Not both. |

Templates use the same `{{name}}` syntax as the [handoff](#templates). Missing names render empty and are reported in the notice; substitution is one pass, so item text cannot inject placeholders.

| Name | Value |
| --- | --- |
| `{{items}}` | The selected items as a readable list: number, badge and title, link, subtitle, state, every field, and the body indented (each body cut to 2,000 characters; the list to 60,000, dropping items from the end with a note). |
| `{{items_json}}` | The selection as `{"title", "total", "items": [...]}` without action commands, cut to 48,000 characters. |
| `{{count}}` | How many items. At most 50 items are used per request. |
| `{{date}}`, `{{job.id}}`, `{{job.title}}`, `{{feed.title}}` | Today's date, the job, and the feed's title. |
| `{{item.id}}`, `{{item.title}}`, `{{item.subtitle}}`, `{{item.badge}}`, `{{item.url}}`, `{{item.state}}`, `{{item.group}}`, `{{item.updated_at}}`, `{{item.body}}` | The **first** selected item (the first of the selection in feed order). |
| `{{item.field.<label>}}` | A field of the first item, by its label in lower case with other characters turned into `_`: `Repo` is `{{item.field.repo}}`, `Snoozed until` is `{{item.field.snoozed_until}}`. |

The rendered prompt is written to `<state dir>/jobs/<id>/work/<unix ms>.md` (the 50 newest are kept) and is the file `{prompt_file}` points at. Because `cwd` and `{{item.*}}` follow the first item, a selection that spans repositories opens in the first item's directory. Run `flockr job validate <id>` to check the templates. `w` needs a server that advertises `feed.work`; an older server only loses this key.

For workbox, the adapter adds a `Repo` field to GitHub and Bitbucket items whose `where` looks like `owner/repo#123`, holding the repository name (`repo`). Jira items have no repository, so they use the default directory. See `examples/jobs/workbox-sync/job.toml` for a commented example that opens in `~/code/work/<repo>`.

## Command line

```sh
flockr job list [--json]          # state, schedule, next run, last result
flockr job status <id>            # settings and recent runs
flockr job run <id> [--wait]      # run now; --wait exits non-zero if the run fails
flockr job logs <id> [-n LINES]   # stdout then stderr of the last run
flockr job enable <id>
flockr job disable <id>
flockr job schedule <id> <every 2h|CRON>   # change timing; see "Change when a job runs"
flockr job env refresh            # capture the login-shell environment again
flockr job new <id> [--template T] [--every I | --schedule C] [--feed] [--handoff]   # scaffold a disabled job
flockr job validate [<id>|<path>] [--run-feed] [--json]   # check a job without waiting for its schedule
flockr job run <id> --dry-run [--no-exec]   # run once here, record nothing, show the feed and handoff
flockr job build <id>             # pre-compile a rust-script job
flockr job schema [--feed]        # JSON Schema for job.toml, or for feed output
flockr job skill                  # print the authoring skill for Claude
```

`new`, `validate`, `run --dry-run`, `build`, `schema` and `skill` need no server; see [Authoring jobs](#authoring-jobs).

Decisions: `flockr decision list|start|snooze|dismiss`, see [Decisions](#decisions).

Feeds:

```sh
flockr feed list [--json]                    # feeds with item and unread counts, staleness
flockr feed show <job> [--json]              # items, their actions and ids, and feed notes
flockr feed refresh <job> [--no-wait]        # run the feed command now; waits and reports by default
flockr feed action <job> <item> <key>        # run an item's action, then refresh the feed
flockr feed adapt workbox [--title T] [--bin PROGRAM]   # stdin: workbox JSON, stdout: a feed
```

`feed refresh` and `feed action` wait for the task and exit non-zero when it fails; `--no-wait` returns once it has started. `feed adapt` needs no server.

## Jobs overlay

`prefix+t` (`keys.jobs`), the global menu entry **jobs**, or **jobs** in the command palette opens a full-screen table: a state dot, the job id and title, the schedule, the next run, and the last result with its duration.

| Key | Action |
| --- | --- |
| `↑`/`↓`, `j`/`k`, `g`/`G` | Move |
| `r` | Run the selected job now (also the `▶ run` button at the end of each row, which a click presses) |
| `l` or `enter` | Show the last run's output (scroll with `j`/`k`, `pgup`/`pgdn`, `g`/`G`; `esc` goes back) |
| `e` | Enable or disable the job |
| `t` | Change the schedule ([how](#change-when-a-job-runs)) |
| `tab` | Switch to the [Decisions](#decisions) list |
| `esc` or `q` | Close |

The footer lists the keys (`r run now · l logs · e enable · t schedule · tab decisions · esc`). A running job shows a turning `◐ run` in place of `▶ run`, its elapsed time in the `next` column and, once the run is over, its result in the status line; the list is asked for every second while a job runs.

The title shows how many decisions are waiting, `[jobs]  decisions (2)`, and a job with decisions pending has a `●N` after its name. The command palette also lists **run job &lt;id&gt;** for every job and **decisions (N)**. Servers without job support show a short explanation instead, and a server without the decision methods only loses the Decisions tab and `t`.

## Plugin jobs

A plugin manifest can declare jobs with `[[jobs]]` tables. They take the same keys as `job.toml`, except `id` is required. The job id is `<plugin id>:<id>`, the working directory is the plugin root, and the job runs with the plugin variables (`FLOCKR_PLUGIN_ID`, `FLOCKR_PLUGIN_ROOT`, `FLOCKR_PLUGIN_CONFIG_DIR`, `FLOCKR_PLUGIN_STATE_DIR`) like plugin actions do. Disabled plugins contribute no jobs.

```toml
[[jobs]]
id = "refresh"
command = ["./refresh.sh"]
every = "30m"
```

## Socket API

| Method | Purpose |
| --- | --- |
| `job.list` | All jobs, a `revision`, and the environment capture status. With `since_revision` equal to the current one it answers `unchanged: true` without the list. |
| `job.get` | One job and its history without output. |
| `job.run` | Start a run: `started: false` when one is already going. |
| `job.set_enabled` | Set the enabled override. |
| `job.set_schedule` | Change a job's schedule (`job_id`, `schedule` as `every 2h` or cron). The answer says where it was stored: `config`, `job_file` or `state`, with a `note` when that was the fallback. |
| `job.logs` | The stdout and stderr tails of a run (`run_id`, `lines` optional). |
| `job.env_refresh` | Start recapturing the login-shell environment in the background. |

Subscribe to `job.run_finished` for `job_id`, `title` and the run record (without output). `job.list`, `job.get`, `job.logs`, `job.run`, `job.set_enabled` and `job.set_schedule` are also available to the Flockr client on the endpoint command lane.

Decision methods:

| Method | Purpose |
| --- | --- |
| `decision.list` | Pending and snoozed decisions, newest first, with a `revision` and the `pending` count. `since_revision` equal to the current one answers `unchanged: true`. `include_resolved` adds started and dismissed ones. `decision_id` with `include_prompt` returns one decision with its rendered `prompt` (cut to 64 KiB). |
| `decision.start` | Open the agent tab. Answers the decision, `tab_id` and `pane_id`. Errors: `decision_not_found`, `decision_resolved`, `decision_cwd_missing`, `decision_prompt_missing`, `decision_command_invalid`, `decision_tab_failed`, `decision_launch_failed`; the decision stays pending with `last_error`. |
| `decision.snooze` | Hide a decision for `for_secs` seconds (default 3600, at most 30 days). |
| `decision.dismiss` | Dismiss it. |

Subscribe to `decision.created` for the new `decision`. The four decision methods are also available to the Flockr client on the endpoint command lane.

Feed methods:

| Method | Purpose |
| --- | --- |
| `feed.list` | A summary of every feed (`title`, `count`, `unread`, `revision`, `stale`, `loaded`, `refreshing`, `error`, `diagnostics`, `last_action`) and a list `revision`. With `since_revision` equal to the current one it answers `unchanged: true` without the feeds. |
| `feed.get` | One feed's summary and its items (`id`, `title`, `subtitle`, `state`, `badge`, `url`, `updated_at` and each action's `key`, `title` and optional `confirm`; never the commands). With `since_revision` equal to the feed's `revision` it answers `unchanged: true` without items. `limit` trims the items, not the `count`. |
| `feed.refresh` | Start a refresh: `started: false` with a `reason` when one is running or the job is. |
| `feed.run_action` | Run an item's action by `job_id`, `item_id` and `key`, then refresh the feed. Unknown items and keys are errors (`feed_item_not_found`, `feed_action_not_found`). |

Subscribe to `feed.updated` for `job_id`, `title`, `revision`, `count`, `unread` and `stale`; it fires when the items, the title or the staleness change, and when an action finishes. All four feed methods are also available to the Flockr client on the endpoint command lane.

## Limits

- Interval jobs run at most once a minute; a run is bounded by `timeout` (at most 24 hours).
- Jobs run on the server's machine. Remote machines run their own jobs.
- Output is stored as the last 16 KiB per stream per run, and 20 runs per job. A feed command's output may be up to 4 MiB.
- A feed holds at most 500 items, and a feed command's action gets at most 60 seconds.
- Cron time zones follow the machine's local time. On Windows the current UTC offset is used for daylight-saving changes.
- A server restart does not stop a job that is still running; its result is not recorded.
- A handoff offers one agent tab per decision. The prompt is capped at 200,000 characters, `{{stdout}}` at 12,000, and at most 50 decisions and 50 prompt files per job are kept.
